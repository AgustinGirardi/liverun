Riesgos

¿Cómo hacemos el push?

  • Push directo a main (recomendada)

    Es lo pedido. Fast-forward, sin force. La CI corre sobre main y dispara el deploy si pasa.

  • Rama + PR

    Se ve la CI antes de mergear y main no se toca hasta que esté verde. Cuesta un paso más.

  • Probar antes con Postgres local (Docker)

    Corre cloud/tests contra postgres:16 local y recién después se pushea. Más lento, pero detecta el problema antes.

  • Push con el deploy desactivado

    Se pausa deploy-portal temporalmente. Requiere tocar variables del repo y acordarse de reactivarlo.

Si falla python-postgres, ¿qué hacemos?

  • Diagnosticar y plan nuevo (recomendada)

    Se lee el log, se identifica la causa y se propone el arreglo con su test. No se cambia nada sin tu OK.

  • Revertir los commits en main

    Deja main sano rápido, pero se pierde el hardening publicado hasta rehacerlo.

  • Arreglo directo sin plan aparte

    Más veloz, pero se saltea la aprobación que pediste para el arreglo.

  • Saltear el test solo en Postgres

    Descartada por los estándares: nunca se saltea un test para que pase la suite.

¿Qué hacemos con el deploy a Cloud Run?

  • Que corra si pasa la CI (recomendada)

    Es el comportamiento actual: deploy-portal necesita python y python-postgres en verde, y verifica /api/health.

  • Pausarlo hasta confirmar python-postgres

    Más cauto, aunque el job ya depende de ese resultado.

  • Desplegar a mano más tarde

    Control total del momento, pero hay que acordarse y Render igual despliega solo.

¿Cómo seguimos la CI?

  • gh run watch hasta el final (recomendada)

    Se queda mirando y reporta el resultado de todos los jobs apenas terminan.

  • Revisar al rato con gh run list

    No bloquea la sesión, pero el resultado llega más tarde.

  • Chequeo periódico programado

    Útil si la CI tarda mucho, pero suma complejidad para una corrida de unos 2 minutos.
