¿Cómo silenciamos el hallazgo de gitleaks?

  • Allowlist por path + valor en .gitleaks.toml (recomendada)

    Un bloque nuevo en la config, acotado al archivo y al valor. Cubre también el commit viejo sin tocar historial ni el test.

  • Cambiar el valor del test a uno de baja entropía

    Evita el hallazgo en commits nuevos, pero el commit 152ea67 sigue marcado: hay que allowlistearlo igual por fingerprint.

  • .gitleaksignore con el fingerprint

    Ignora solo ese hallazgo exacto. Es muy preciso, pero se rompe si cambia el commit o la línea.

  • Reescribir historial

    Exige force-push sobre un commit ya publicado. Descartada por riesgosa.

¿Qué condición usamos entre path y valor en la allowlist?

  • condition = "AND" (recomendada)

    Solo se ignora ese valor en ese archivo. Es lo más acotado; se confirma que 8.30.1 lo soporta.

  • Dejar el default (OR)

    Igual que el bloque existente: más simple, pero ignora todo el archivo o ese valor en cualquier lado.

  • AND en el nuevo y también arreglar el bloque viejo

    Más prolijo, pero amplía el alcance del pedido; iría mejor en un commit aparte.

¿Cómo conseguimos gitleaks para correrlo local?

  • Binario oficial v8.30.1 en un directorio temporal (recomendada)

    Misma versión que la CI, con checksum verificado y fuera del repo. No instala nada global.

  • Docker (zricethezav/gitleaks:v8.30.1)

    Aislado y con versión fija, pero requiere tener Docker andando.

  • winget o scoop

    Cómodo, pero instala globalmente y se controla menos la versión.

¿Cómo llevamos el cambio a main y seguimos la CI?

  • Commit chico + push a main + gh run watch (recomendada)

    Lo que pediste: sube también el commit de planes y se sigue el run hasta que todo pase.

  • Abrir un PR

    Se ve la CI antes de mergear, pero agrega un paso y demora el push del commit de planes.

  • Pushear primero los planes y después el fix

    Separa los efectos, pero genera dos corridas de CI y una probablemente falla por gitleaks.
